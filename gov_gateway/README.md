# CSAP Government Gateway (simulated registries)

A separate service that represents the government portals CSAP verifies bidders against. Each
registry has **its own data file** in `data/`; every answer is looked up in that file (re-read
on each request, so edits take effect immediately). All records are fictitious and are
regenerated by `data/generate_datasets.py`. In production each registry is replaced by a real
integration (API Setu, a GSTN GSP, a commercial KYC provider) behind the same backend adapter
(`backend/src/registries/adapters.ts`), so CSAP's screens do not change.

```bash
# from the repo root (uses the ai_engine virtualenv)
npm run dev:gateway      # http://localhost:8100
npm run test:gateway
```

On Vercel it is served at `/api/gov/*` (the old `/api/pan-registry/*` path still works).

## API

All endpoints except health need header `x-api-key` (env `PAN_API_KEY`, default `csap-demo-pan-key`).

| Endpoint | Body | Data file |
| --- | --- | --- |
| `POST /v1/pan/verify` | `{ "pan", "name"? }` | `pan.json` |
| `POST /v1/gstn/lookup` | `{ "identifier": GSTIN }` | `gstn.json` (status, GSTR-3B filing history) |
| `POST /v1/udyam/lookup` | `{ "identifier": Udyam number }` | `udyam.json` (enterprise category) |
| `POST /v1/mca21/lookup` | `{ "identifier": CIN }` | `mca21.json` (company status, directors) |
| `POST /v1/epfo/lookup` | `{ "identifier": establishment code }` | `epfo.json` (latest ECR month) |
| `POST /v1/esic/lookup` | `{ "identifier": employer code }` | `esic.json` (latest contribution month) |
| `POST /v1/startup_india/lookup` | `{ "identifier": DIPP number }` | `startup_india.json` |
| `POST /v1/nsic/lookup` | `{ "identifier": NSIC number }` | `nsic.json` |
| `POST /v1/debarment/check` | `{ "pan"?, "gstin"?, "name"?, "as_of"? }` | `debarment.json` |
| `POST /v1/digilocker/issued` | `{ "identifiers": [..] }` | `digilocker.json` |
| `GET /v1/registries` | | catalogue with dataset versions |
| `GET /v1/health` | | |

Lookups answer `FOUND` (with `record`), `NOT_FOUND`, or HTTP 400 `INVALID_FORMAT`. Every
response carries `source` (dataset, file, version), `request_id`, `timestamp` and `lookup_ms`.

### PAN examples

| Situation | Example PAN | Result |
| --- | --- | --- |
| Valid, name matches | `AABCA1234F`, `ABCDE1234A` | `VALID`, `name_match: MATCH` |
| Valid, name does not match | `AAGCK5566L` (sent with "Kaveri Safety Equipment…") | `VALID`, `name_match: NO_MATCH` |
| Invalid / deactivated | `AAECS7788K` / `AAFCR3322Q` | `INVALID` / `DEACTIVATED` |
| Not in registry | `AAHCZ9090P` | `NOT_FOUND` |
| Malformed | `12345ABCDE` | HTTP 400 `INVALID_FORMAT` |

To test with your own PAN, add a record to `data/pan.json` (never commit a real PAN).
